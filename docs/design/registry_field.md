# 设计：`CoherentInterfaceConfig` 的 `registry` 字段

**状态**：提案，未实现。针对 **v0.4.1** 撰写，目标 0.5.0。
**一句话**：让用户可以**请求**一个界面注册位点，并把"请求了什么、实际摆在哪、松弛后停在哪"三件事都记进 provenance。

---

## 1. 缺的到底是什么

`_assemble_interface` 从来没有"面内定位"这一步。PR #30 加了一个**极窄的**：
仅当 as-built 横向偏移 < `ON_TOP_LATERAL_TOL`（1e-6 Å）时，沿衬底堆垛矢量平移 film。
注册本身是**事后测量**（`metadata.registry_lateral_offset_ang`），只告警、不选择。

后果（这就是 `registry` 字段存在的理由）：

- 非 (001) 取向报出的 γ_int **属于一个没人挑过的位点**；
- 同一份厚度扫描里，起始位点随 `--min-thickness` 变化 → 厚度不是单变量；
- 用户无法要求"我要 fcc 空位"，只能接受切割给的那个。

## 2. 决定设计形态的那个实测：增量式 ≠ 目标式

PR #30 实现的是**增量式**：把衬底堆垛步**加到切割留给你的位置上**。
在 (111) 上切割把 film 留在 on-top（偏移 0），于是 0 + 堆垛步 = fcc 空位 —— 对。
在 (110) 上切割把 film 留在 ridge（½,0），于是 ridge + 堆垛步 = (0,½) = **short-bridge** —— 错。

Cu/Ni(110) @14.4 Å，同一环境、同一协议，只有摆放不同。四臂的 `E_interface`
与归档自己四位点扫描的结果**逐位一致（六位小数）**，所以这张表的每一格都有对照：

| 摆放方式 | 位点（面内分数） | γ_int (J/m²) | E_interface (eV) | 归档值 |
|---|---|---|---|---|
| 当前 as-built | ridge (½, 0) | 0.5952 | −115.099365 | 0.5952 / −115.099365 |
| **加堆垛步（增量式外推）** | short-bridge (0, ½) | **1.5189** | −114.566643 | 1.5189 / −114.566643 |
| **摆到 top+堆垛步（目标式）** | trough (½, ½) | **0.0881** | −115.391869 | 0.0881 / −115.391869 |
| 摆到 (0,0) | on-top (0, 0) | 2.0332 | −114.270020 | 2.0332 / −114.270020 |

**结论：把 (111) 的规则照搬到 (110) 会让结果差 2.55 倍**（0.5952 → 1.5189），而
正确的目标式摆放拿到扫描最小值 0.0881（比 ridge 低 6.8 倍）。四种摆放全部收敛、
`valid=True`、fmax 达标、OOD 无告警——正是这个包存在的意义所要防的那类失败：
**看起来可信，但属于一个没人挑过的位点。**

两种表述在 (111) 上恰好等价、在 (110) 上分道扬镳，所以
**`registry` 必须是"目标式"：先定点位，再算需要平移多少**，而不是"加一个增量"。

## 3. 提议的接口

```python
registry: str | tuple[float, float] | None = None
```

| 取值 | 含义 | 何时可用 |
|---|---|---|
| `None`（默认） | 今天的全部行为，逐位不变 | 总是 |
| `"auto"` | 摆到**延续衬底堆垛序列**的位点，即 `衬底顶层原子 + 堆垛步` | 总是（堆垛步可直接读出） |
| `"on-top"` | 摆到 `(0,0)`：正对衬底顶层原子 | 总是 |
| `"hcp"` | 密排面上"另一个"空位 | 仅当该表面可分辨出 ≥3 个亚晶格 |
| `(u, v)` | 界面胞内的显式分数面内偏移 | 总是 |

不在词汇表内的名字（`fcc-hollow`、`trough`、`ridge`、`bridge`、`short-bridge`…）
**报错而不是猜**，错误信息里列出该表面实际能分辨的位点表。

## 4. 为什么不做"全名字典"

因为**位点名是取向与晶格相关的，无法一般地解析**：

- fcc(111) 的高对称位点是 (0,0)、(⅓,⅓)、(⅔,⅔)；
- fcc(110) 的是 (0,0)、(½,0)、(0,½)、(½,½)；
- 而且 (111) 上哪个叫 fcc、哪个叫 hcp，取决于更深层原子的位置；(110) 的
  ridge/trough 根本不在亚晶格位置上，是两条原子行之间的中点。

所以：小词汇表（都能算出来）+ 显式 `(u,v)`（永远能用）+ 一个**只读的位点枚举
helper**（`enumerate_registry_sites(atoms)`，返回"这个表面我能看见哪些位点"），
让用户按名字挑得到就挑、挑不到就写 `(u,v)`。**不承诺一般性的名字解析。**

## 5. 对现有行为的影响（已实测，非推断）

`registry="auto"`（目标 = 衬底顶层 + 堆垛步）在三个取向 × 四档厚度上的实测：

| 取向 | as-built 偏移 | 堆垛步 | 目标式的位移 |
|---|---|---|---|
| (001) 10.8/14.4/18.0/21.6 | (0, ½) | (0, −½) | **恒等（四档全不动）** |
| (111) 10.8 / 14.4 / 18.0 | (⅓, ⅓) | (⅓, ⅓) | **恒等** |
| (111) 21.6 | (−⅓, −⅓) | (⅓, ⅓) | 移动 1.4758 Å（hcp → fcc） |
| (110) 10.8/14.4/18.0/21.6 | (½, 0) | (−½, −½) | 移动 1.2781 Å（ridge → trough） |

两点值得写进提案：

1. **(001) 全程恒等。** (001) 是唯一有 DFT 交叉验证的取向，动了它会推翻已验证
   的数。目标式规则在它上面自动是恒等，这是这个规则能当默认值的前提。
2. **(111) 的厚度扫描重新变成单变量。** 目前（含 PR #30 之后）四档的起始位点是
   fcc / fcc / fcc / hcp，`--min-thickness` 仍不是干净的单变量。`"auto"` 让四档
   全部从 fcc 出发。代价：21.6 档从 hcp 变 fcc，γ_int 0.0811 → 0.0812（1e-4 量级），
   但**可解释性的收益远大于这点数值差**。

## 6. 必须记进 provenance 的三件事

每个 candidate 都要带：

- `registry_requested`：用户要的（字符串或 `(u,v)`；`None` 表示没要）；
- `registry_as_built_frac` / `registry_as_built_lateral_A`：摆放后、松弛前实测；
- `registry_final_frac` / `registry_final_lateral_A`：**松弛后**实测。

第三条不能省：归档里已有 (110)@21.6 在松弛中从 ridge 滑到 trough 的记录，
as-built 的位点不等于最终位点。只记前者会让人把"摆在哪"当成"停在哪"。

## 7. 必须拒绝、不能将就的几种情况

- 词汇表外的字符串 → `validate()` 报错，列出可用值与该表面可见位点；
- `(u,v)` 长度不是 2 → 报错；
- 摆放后实测偏移与请求值偏差超容差 → **报错，不静默回退**到 as-built。
  （一致原则：这个包对"静默产出另一个东西"的处理方式是抛错，见 `GeometryGateError`。）
- 无法识别原子层（`_atomic_planes` 少于 2 层）→ 记入 candidate 的 invalid 原因，
  不假装完成摆放。

### 一个实现上会踩的坑（实测踩过）

换算必须是"**先取分数坐标 → 回绕 → 再乘回笛卡尔**"。回绕一个笛卡尔差是无意义的
（晶格一般不是立方的），而且**不会报错**：film 会被摆到一个偏移了约 0.31 个晶格
常数的位置，看起来像"注册没生效"，实测表现为 film 在松弛中滑走、能量落到一个
与请求位点无关的值。本次 (110) on-top 那一臂就因此先给出了 0.090（假），
修正后是 2.0332（真，与归档逐位一致）。所以第 11 节的"目标命中"测试不能省。

## 8. 与 non-(001) 告警的关系

告警现在的措辞是"注册没有扫过、也没有字段可以请求"——`registry` 落地后后半句变假，
必须改：改成"你请求了位点 X，builder 已把它摆在那里；但这仍然不是对其余位点的扫描"。

**只有 `registry="scan"`（第 10 节）才能真正撤掉告警。**

## 9. 需要拍板的决定：默认值是 `None` 还是 `"auto"`

- **`None`（保守）**：0.4.1 的数字全部不变；用户想要正确位点得自己开口。
  代价：默认仍然输出归档自己标注为"驻点假象"的 0.5952（(110) ridge，比扫描最小值
  高 6.8 倍），而这个包的存在理由就是不让这种数字静默流出。
- **`"auto"`（推荐）**：修掉 (110) 的 6.8 倍偏差，并让 (111) 厚度扫描变单变量。
  代价：**(110) 上 0.4.1 及更早的所有数值都会变**（0.595 → 0.088），归档的 ridge
  行要像 0.898 那样标成"修复前记录"——这个流程我们已经跑通两次（#31、#32），
  不是新开销。

推荐 `"auto"`，因为"字段有了但默认仍产出已知假象"是半个措施；而改动本身
**不小声**：minor 版本号、CHANGELOG 条目、归档注记三件套齐全。

## 10. 第二阶段：`registry="scan"`

一次构建产出 N 个 candidate，每个对应一个可分辨的高对称位点，各自松弛、各自报
γ_int。这才是"引用非 (001) 的 γ_int"的正确姿势（归档的 `registry_scan_111.py`
就是手工这么做的）。接口形态：`registry="scan"` + `max_registry_sites: int | None`。
这一阶段完成后 non-(001) 告警才能撤。

## 11. 测试计划

- **恒等性**：`registry=None` 相对 v0.4.1 在 (001)/(110) 全档、以及 (111) 非 on-top
  族上**逐位相同**（同进程 A/B，断言 `array_equal`，不用 `allclose`）。
- **目标命中**：请求 builder 本来就产的位点 → 位移为零，断言 `array_equal`；
  请求 (110) 的 (0,0)/(½,½)/(0,½) 与 (111) 的 (0,0)/(⅓,⅓) → 实测落点与请求值
  吻合到 1e-6。
- **物理验收**（这条最有价值）：`registry` 请求各位点应**复现归档四位点扫描的
  数值**——(110)@14.4 的 ridge 0.5952 / short-bridge 1.5189 / trough 0.0881；
  (111)@18.0 的 on-top 0.8980 / fcc 0.0812 / hcp 0.0810。
- **provenance**：三个 registry 字段齐全；松弛后位点与 as-built 不同时两者都留。
- **拒绝路径**：坏字符串、坏长度 `(u,v)`、摆放偏差超限 → 报错且错误信息含可用值。
